# Список необходимых исправлений перед заполнением экспериментальной части статьи

**Документ подготовлен по результатам проверки:**

- архива `models.zip`;
- текущей версии статьи `Статья.docx`;
- `EXPERIMENT_PROTOCOL.md`;
- `ARTICLE_EXPERIMENT_PLAN.md`.

## 0. Итоговый экспертный статус

Экспериментальная часть статьи **пока не готова к финальному заполнению**. Текущий архив содержит полезные промежуточные результаты, но он не закрывает требования экспериментального плана: нет воспроизводимого аудита датасета, нет подтверждённого честного `test`, нет независимого `test_metrics.json`, нарушена трассировка конфигураций, а в `test`-предсказаниях присутствуют аугментированные копии исходных изображений.

Текущая версия статьи содержит численные утверждения и выводы, которые **не подтверждаются архивом**. До пересборки экспериментов их нельзя оставлять в финальной версии.

Критические блокеры:

1. `test` содержит аугментированные изображения.
2. Отсутствуют обязательные артефакты `prepare`: `raw_dataset_audit.json`, `split_manifest.csv`, `train_augmentation_manifest.csv`, `dataset_audit.json`, `prepare_summary.json`.
3. Отсутствует независимый `test_metrics.json`.
4. В архиве нет подтверждённых артефактов по крупным сеянцам.
5. Для YOLO-запусков `container_recall = 0.0`, что требует диагностики.
6. Cell-level метрики показывают слабое выявление множественных ячеек и целей удаления.
7. Baseline есть, но его нужно оформить и пересчитать строго по тому же `test`.
8. В статье используются слишком сильные формулировки: «уверенно распознаёт», «успешно формирует», «подтверждает применимость», хотя текущие артефакты этого не доказывают.

## P0.1. Пересобрать датасет: split должен быть выполнен до аугментации

### Проблема

В архивных `predictions.json` для `test` обнаружены изображения с суффиксами:

```text
_filter
_flip
_scale
```

Фактическая картина по `test`-предсказаниям:

```text
изображений в predictions.json: 48
уникальных базовых изображений после удаления суффиксов аугментации: 14
явно аугментированных изображений: 42 из 48
```

Это означает, что `test` не является независимой исходной выборкой. Такой `test` завышает воспроизводимость и нарушает базовое требование: аугментация допустима только для `train`, а не для `val/test`.

### Что исправить

1. Собрать исходный датасет без аугментаций:

```text
raw_seedlings/
  images/
  labels/
```

2. Проверить, что в `images/` нет файлов с признаками аугментации:

```text
_filter
_flip
_scale
_rotate
_crop
_brightness
_contrast
```

3. Запустить `prepare`, который сначала делит исходные изображения на `train/val/test`, а затем применяет аугментацию только к `train`.

4. Если несколько файлов относятся к одному контейнеру, дате, лотку или сцене, задать `dataset.split.group_regex`, чтобы близкие изображения попадали только в один split.

### Обязательные выходные файлы

После исправления должны быть сохранены:

```text
raw_dataset_audit.json
data.yaml
split_manifest.csv
train_augmentation_manifest.csv
dataset_audit.json
prepare_summary.json
```

### Критерий готовности

В `val` и `test` должны быть только исходные независимые изображения. Ни один базовый кадр из `train` не должен иметь аугментированную или близкую копию в `val/test`.

### Что изменить в статье

В разделе «Сбор и подготовка датасета» текущую формулировку вида:

> После применения методов аугментации объём выборки был увеличен до ... Разбиение на обучающую, валидационную и тестовую выборки выполнялось в соотношении 70/20/10.

нужно заменить на более строгую:

> Исходный набор данных был сначала разделён на обучающую, валидационную и тестовую части на уровне исходных изображений/групп сцен. Аугментация применялась только к обучающей части, чтобы исключить попадание близких копий одного изображения в валидационную и тестовую выборки.

После этого привести реальные числа по `raw` и `prepared`-аудитам.

## P0.4. Заново выполнить `predict` и `evaluate-cells` на корректном test

### Проблема

Текущие `cell_metrics.json` посчитаны по `predictions.json`, где `test` содержит аугментированные копии. Следовательно, эти cell-level метрики нельзя использовать как финальные.

### Что исправить

После независимого `test` выполнить:

```powershell

py -m seedling_experiments evaluate-cells --config configs/article_yolo11n.yaml
```

Сохранить:


### Какие метрики обязательно вынести в статью

| Группа | Метрики |
|---|---|
| Классификация ячеек | `cell accuracy`, `macro precision`, `macro recall`, `macro-F1` |
| Множественные ячейки | `precision`, `recall`, `F1` для класса `multiple` |

Финальная таблица должна показывать не только `cell accuracy`, но и `multi-cell recall` и `target recall`. Для задачи лазерного прореживания именно они являются ключевыми.

## P0.7. Диагностировать `container_recall = 0.0` у YOLO

### Проблема

Во всех YOLO-запусках архива `container_recall = 0.0`. Это не обязательно означает, что контейнеры визуально не обнаруживаются, но это означает, что в текущей процедуре `evaluate-cells` GT-контейнеры не сопоставлены с предсказанными контейнерами по IoU.

Возможные причины:

- bbox контейнеров размечены и предсказаны по разным правилам;
- `container_class` и `seedling_class` перепутаны;
- модель предсказывает фрагменты контейнера вместо одного bbox;
- postprocessing контейнеров используется в визуализации, но не используется в `evaluate-cells`;
- `container_iou` слишком высок для текущей геометрии;
- `predictions.json` содержит разные поля `detections` и `containers`, а evaluator читает не то поле.

### Что исправить

1. Для 10–20 изображений вручную сравнить GT bbox контейнера и predicted bbox контейнера.
2. Посчитать распределение IoU контейнеров.
3. Проверить соответствие классов:

```text
0 = container
1 = seedlings
```

4. Проверить, какие поля `predictions.json` использует `evaluate-cells`:

```text
detections
containers
```

5. Принять одно из двух решений:

#### Вариант A. End-to-end оценка

Оставить:

```yaml
evaluation:
  use_ground_truth_containers: false
```

Тогда нужно исправить детекцию/сопоставление контейнеров и отдельно отчитаться по `container_recall`.

#### Вариант B. Оценка матрицы при известной геометрии контейнера

Установить:

```yaml
evaluation:
  use_ground_truth_containers: true
```

Тогда в статье явно написать:

> Cell-level метрики рассчитаны при известной геометрии контейнера и не являются полной end-to-end оценкой качества детекции контейнеров.

### Что изменить в статье

Нельзя писать:

> Нейросеть уверенно распознаёт контейнеры.

Пока `container_recall = 0.0`, корректная формулировка:

> В текущем контуре оценивания качество сопоставления контейнеров требует отдельной диагностики. Для анализа распределения сеянцев по ячейкам может использоваться режим с известной геометрией контейнера; в этом случае cell-level метрики не интерпретируются как полная end-to-end оценка системы.

## P0.9. Проверить эвристику «оставить самый большой bbox»

### Проблема

В текущей постановке предполагается, что в множественной ячейке сохраняется сеянец с максимальной площадью bbox, а остальные удаляются. Это инженерная эвристика, а не доказанный биологический критерий развитости.

Особенно опасный случай: заваленный или наклонённый сеянец может иметь больший bbox, чем более жизнеспособный вертикальный сеянец.

### Что исправить

Подготовить экспертную таблицу хотя бы для подвыборки множественных ячеек:

```text
image, container_id, row, col, keep_seedling_id, remove_seedling_ids, comment
```

Сравнить автоматическое решение с экспертным:

```text
keep accuracy
remove precision
remove recall
ошибка выбора сохраняемого сеянца
```

### Что изменить в статье

Добавить ограничение:

> Критерий максимальной площади bbox используется как базовая эвристика выбора сохраняемого сеянца. Он не всегда эквивалентен биологической развитости растения, особенно при наклоне или заваливании побега; поэтому требуется отдельная экспертная валидация правила keep/remove.

## P1.5. Исправить математическую постановку задачи

### Проблема

В текущей версии статьи формулы частично потеряли обозначения: встречаются фрагменты вида «изображение контейнеризированных сеянцев , где — высота», «задаётся вектором при условиях и», «Все пороги были установлены на уровне». В таком виде раздел не является математически корректным.

Также есть опечатки:

```text
сеянеу
детекции нахождения сеянца
если то.
```

### Что исправить

Нужно заново набрать постановку задачи в строгом виде.

### Минимальный набор определений

```text
I ∈ R^{H×W×3} — входное RGB-изображение.
B = (x_1, y_1, x_2, y_2), где 0 ≤ x_1 < x_2 ≤ W, 0 ≤ y_1 < y_2 ≤ H.
area(B) = (x_2 - x_1)(y_2 - y_1).
c(B) = ((x_1+x_2)/2, (y_1+y_2)/2) — центр bbox.
IoU(B_i, B_j) = area(B_i ∩ B_j) / area(B_i ∪ B_j).
```

Для контейнера:

```text
C_i = (B_i^c, s_i^c), где B_i^c — bbox контейнера, s_i^c — confidence.
```

Для сеянца:

```text
S_j = (B_j^s, s_j^s), где B_j^s — bbox сеянца, s_j^s — confidence.
```

Разбиение контейнера:

```text
G_i = {g_{i,r,q} : r = 1..R, q = 1..Q}
```

Назначение сеянца ячейке:

```text
S_j назначается ячейке g_{i,r,q}, если c(B_j^s) ∈ g_{i,r,q}
```

или, если используется IoU/перекрытие с ячейкой, явно определить правило.

### Что обязательно уточнить

1. Размер сетки: `R × Q`, например `11 × 11`.
2. Порог confidence контейнера.
3. Порог confidence сеянца.
4. Порог IoU контейнера.
5. Правило назначения сеянца в ячейку: центр bbox или overlap.
6. Что происходит, если bbox сеянца пересекает несколько ячеек.
7. Что происходит, если контейнер не найден.
8. Правило формирования `removal_targets`.
9. Как сравниваются predicted targets и GT targets.
10. Как считается coordinate error.

### Критерий готовности

Раздел должен быть понятен без доступа к коду. Читатель должен иметь возможность реализовать evaluator по описанию в статье.

# 8. Главный научный риск

Главный риск статьи сейчас не в том, что модель даёт невысокие метрики для мелких сеянцев. Это нормальный научный результат, если он честно показан.

Главный риск — в том, что текущая версия статьи делает выводы сильнее, чем позволяют артефакты. Рецензент атакует не сам факт низкого recall, а отсутствие независимого test, утечку аугментаций, неподтверждённые числа и непрозрачную трассировку экспериментов.

После исправления протокола даже умеренные результаты можно защитить как честный baseline и основу для дальнейшего развития метода. Без исправления протокола даже высокие числа будут методологически слабыми.
