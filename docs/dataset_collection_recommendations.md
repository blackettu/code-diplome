# Рекомендации по сбору набора данных для проекта автоматизированного удаления сорняков и лишних всходов в кассетах ЗКС

**Версия:** 0.1  
**Дата:** 2026-06-07  
**Статус:** рабочий методический документ для планирования сбора данных  
**Контекст:** проект `blackettu/code-diplome`, текущий экспериментальный контур для детекции контейнеризированных сеянцев, построения матриц заполнения ячеек и оценки целей удаления.  
**Главный тезис:** набор данных должен проектироваться не как набор картинок для YOLO, а как измерительный инструмент для проверки полной задачи: `изображение кассеты → состояние ячеек → кандидаты на удаление → координаты действия → безопасное решение`.

**Принцип терминологии:** в основном тексте используются русскоязычные термины. Машинные имена классов, полей, команд и каталогов оставлены в обратных кавычках только там, где они нужны для совместимости с кодом, разметкой или конфигурационными файлами. При первом появлении такие имена поясняются: например, `stem_base_point` — это не новый биологический термин, а имя поля для координаты основания стебля на изображении.

## 1. Краткий экспертный вердикт

Сбор набора данных — критический этап проекта. Ошибки здесь почти невозможно исправить последующим выбором модели. Если собрать данные без строгой онтологии классов, метаданных, группового разбиения, контроля качества разметки и калибровки, то можно получить высокие `mAP` или `accuracy`, но эти метрики не будут доказывать пригодность системы для промышленного удаления сорняков.

На текущем этапе нельзя ограничиваться форматом:

```text
images/
labels/
```

Такого формата достаточно только для первичного обучения детектор объектов. Для научной статьи и будущего продукта нужны дополнительные уровни данных:

- изображение кассеты;
- геометрия контейнера и ячеек;
- разметка отдельных экземпляров растений;
- состояние каждой ячейки;
- признак целевого/нецелевого растения;
- координата безопасного воздействия;
- неопределённость или флаг сомнительного случая;
- метаданные съёмки;
- калибровка камеры и рабочей плоскости;
- протокол разбиения;
- протокол контроля качества разметки;
- отдельный независимый тестовая выборка.

Главная методологическая опасность: собрать много похожих изображений одной и той же кассеты, случайно распределить почти одинаковые кадры между `train`, `val` и `test`, получить завышенные метрики и сделать ложный вывод о готовности модели. Для проекта с исполнительным механизмом это особенно опасно: ошибка распознавания становится физическим действием.

## 2. Какая именно задача должна быть покрыта набором данных

Перед съёмкой надо письменно зафиксировать, какую задачу решает версия набора данных. Иначе позже возникнет соблазн использовать один и тот же набор для разных утверждений, не имея для этого валидной разметки.

### 2.1. Минимальная задача ближайшего этапа

Ближайшая реалистичная задача:

> По изображению кассеты с сеянцами ЗКС определить геометрию кассеты, состояние каждой ячейки и кандидаты на удаление в ячейках с множественным прорастанием.

Для неё достаточно следующих сущностей. В скобках указаны возможные машинные имена классов или состояний, которые могут использоваться в разметке и конфигурациях:

- кассета или контейнер (`container` или `tray`) — видимая рабочая область с регулярной сеткой посадочных ячеек;
- целевой сеянец (`seedling`) — выращиваемое растение, которое обычно надо сохранить;
- пустая ячейка (`cell_empty`) — посадочная ячейка без видимого растения;
- ячейка с одним целевым растением (`cell_single`) — нормальное состояние, если технологически требуется один сеянец в ячейке;
- ячейка с несколькими целевыми растениями (`cell_multiple`) — состояние, при котором может потребоваться прореживание;
- сомнительный случай (`uncertain`) — изображение, ячейка или объект, по которому эксперт не уверен; такие случаи нельзя использовать как обычную эталонную разметку без дополнительного решения.

Класс `weed` не следует добавлять формально, если нет экспертной разметки сорняков. Иначе модель будет учиться на субъективных и нестабильных метках.

### 2.2. Расширенная задача для удаления сорняков

Для реального удаления сорняков нужна более строгая постановка:

> По изображению кассеты определить целевые растения, сорные растения, лишние целевые всходы, безопасные точки воздействия и запрещённые зоны вокруг сохраняемых сеянцев.

Для неё нужны дополнительные сущности. Здесь важно различать биологический статус растения, технологическое решение и геометрическую координату:

- целевой сеянец (`crop_seedling`) — растение выращиваемой культуры, которое должно быть сохранено, если оно не признано лишним в конкретной ячейке;
- лишний целевой всход (`extra_crop_seedling`) — целевое растение в ячейке с несколькими всходами, которое можно удалить при прореживании; это не сорняк;
- сорное растение (`weed`) — нежелательное растение, не относящееся к целевой культуре и подлежащее удалению; такая метка должна подтверждаться агрономом;
- растение неизвестного статуса (`unknown_plant`) — объект, похожий на растение, но без надёжного решения «целевая культура / сорняк / лишний всход»;
- зона запрета действия (`do_not_act_zone`) — область изображения, в которой исполнительный механизм не должен работать из-за риска повреждения сохраняемого растения, кассеты или постороннего объекта;
- точка воздействия (`action_point`) — координата, куда предполагается направить рабочий орган; это может быть основание стебля, точка роста или другая агрономически обоснованная точка;
- основание стебля (`stem_base`) — место выхода стебля из субстрата; для молодых растений оно часто важнее центра листьев;
- состояние ячейки (`cell_state`) — итоговое описание ячейки: пустая, один целевой сеянец, несколько целевых сеянцев, есть сорняк, требуется проверка и т. п.;
- кандидат на удаление (`removal_candidate`) — конкретное растение или объект, для которого система предлагает операцию удаления;
- требуется проверка оператором (`human_review_required`) — флаг, означающий, что автоматическое действие запрещено или нежелательно без человека.

Принципиально важно: **центр ограничивающей рамки не равен безопасной точке удаления**. У молодого растения ограничивающая рамка часто описывает листья, а не основание стебля. Для механического или лазерного воздействия точка действия должна быть биологически осмысленной: основание стебля, точка роста, центр нежелательного растения или иная точка, выбранная агрономом и инженером.

### 2.3. Что набор данных не должен доказывать преждевременно

На ранней стадии набор данных не должен использоваться для утверждений:

- система готова к автономному удалению сорняков;
- лазерное воздействие безопасно для сохраняемых сеянцев;
- модель обобщается на другие питомники;
- RL-агент улучшает промышленный процесс;
- координаты в пикселях автоматически пригодны для исполнительного механизма;
- высокая `mAP` означает низкий риск повреждения растений.

Такие утверждения требуют отдельных данных и отдельных экспериментов.

## 3. Термины и единицы разметки

Нужно заранее договориться о словаре. Без этого разные разметчики будут размечать один и тот же объект по-разному.

| Термин или имя поля | Рабочее определение | Нюанс |
|---|---|---|
| Кассета / контейнер (`tray`, `container`) | Физическая кассета или её видимая рабочая область, внутри которой расположена регулярная сетка посадочных ячеек. | Нужно заранее решить, размечается внешний край кассеты, внутренняя область ячеек или только рабочая область, доступная исполнительному механизму. |
| Ячейка (`cell`) | Одна посадочная ячейка кассеты. | Если сетка регулярная, надо фиксировать число строк и столбцов, начало отсчёта и ориентацию: какая ячейка считается строкой 0, столбцом 0. |
| Целевой сеянец (`crop_seedling`, иногда `seedling`) | Выращиваемое растение, которое по умолчанию надо сохранить. | Нужна связь с породой, видом, партией семян и возрастом растений. |
| Сорное растение (`weed`) | Нежелательное растение, не являющееся целевой культурой и подлежащее удалению. | Решение должно быть подтверждено агрономом; на ранней стадии морфология может быть неоднозначной. |
| Лишний целевой всход (`extra_crop_seedling`) | Целевое растение в ячейке, где технологически надо оставить один сеянец. | Это не сорняк, но для исполнительного механизма это тоже цель удаления. |
| Растение неизвестного статуса (`unknown_plant`) | Объект, похожий на растение, но без надёжного решения о его биологическом или технологическом статусе. | Не смешивать с сорняком; иначе модель будет получать шумную метку. |
| Ограничивающая рамка (`bbox`) | Прямоугольник вокруг видимой части объекта на изображении. | Рамка удобна для обучения детектора, но её центр не обязан совпадать с безопасной точкой удаления. |
| Маска объекта (`mask`) | Область пикселей, принадлежащих конкретному объекту. | Нужна, когда листья перекрываются или рамка слишком груба для выбора точки действия. |
| Ключевая точка (`keypoint`) | Одна размеченная координата на объекте: например основание стебля или точка воздействия. | Если исполнительный механизм должен попасть в точку, эту точку надо размечать явно, а не вычислять из рамки. |
| Точка основания стебля (`stem_base_point`) | Координата на изображении, соответствующая месту выхода стебля из субстрата. | Это машинное имя поля. Биологически речь идёт об основании стебля, а не о центре листьев. |
| Основание стебля (`stem_base`) | Само место выхода стебля из субстрата. | Может быть плохо видно из-за листьев, субстрата, тени или ранней стадии роста. |
| Точка воздействия (`action_point`) | Координата, куда должен быть направлен рабочий орган: лазер, механический инструмент или иной исполнительный механизм. | Для продукта важнее центра ограничивающей рамки. Точка должна иметь физический смысл и оценку неопределённости. |
| Зона запрета действия (`forbidden_zone`, `do_not_act_zone`) | Область, где исполнительный механизм не должен действовать. | Нужна для правил безопасного принятия решений, даже если первая модель её ещё не использует. |
| Состояние ячейки (`cell_state`) | Итоговая классификация ячейки: пустая, один сеянец, несколько сеянцев, сорняк, смешанный случай, сомнительный случай. | Это уровень прикладной задачи; его нельзя полностью заменить метриками детекции отдельных объектов. |
| Кандидат на удаление (`removal_candidate`) | Растение или объект, который система предлагает удалить. | Кандидатом может быть сорняк или лишний целевой всход. |
| Требуется проверка оператором (`human_review_required`) | Признак случая, где автоматическое действие нельзя выполнять без человека. | Такой флаг должен быть нормальным исходом системы, а не ошибкой модели. |
| Разбиение набора данных (`split`) | Разделение данных на обучающую, валидационную и тестовую части. | Разбиение должно выполняться по группам кассет или съёмочных сессий, а не случайно по отдельным изображениям. |
| Обучающая выборка (`train`) | Часть данных, на которой модель обучается. | Только к ней можно применять искусственное расширение данных. |
| Валидационная выборка (`val`) | Часть данных для настройки порогов, параметров и выбора модели. | Её нельзя подменять тестовой выборкой. |
| Тестовая выборка (`test`) | Замороженная часть данных для финальной оценки. | Если её использовали для выбора модели, она больше не является честной тестовой выборкой. |
| Базовый метод сравнения (`baseline`) | Простой метод, с которым сравнивают основную модель. | Он нужен, чтобы доказать, что сложная модель даёт реальное преимущество. |
| Автоматическая проверка (`audit`) | Скриптовая проверка целостности изображений, меток, координат, классов и разбиений. | Не заменяет экспертную проверку биологического смысла разметки. |
| Метаданные (`metadata`) | Сведения о съёмке, кассете, культуре, камере, освещении, операторе и версии разметки. | Без них невозможно доказать независимость теста и объяснить ошибки переноса на новые условия. |

## 4. Онтология классов: не смешивать биологию, решение и геометрию

Одна из типичных ошибок — сделать слишком простой список классов: `container`, `seedling`, `weed`. Для научного проекта этого недостаточно. В наборе данных должны быть разделены три уровня.

### 4.1. Геометрический уровень

Этот уровень отвечает на вопрос: «где находится объект?»

- рамка или многоугольник кассеты (`tray_bbox` или `tray_polygon`) — граница рабочей области кассеты;
- сетка ячеек (`cell_grid`) — правило разбиения кассеты на строки и столбцы;
- ограничивающая рамка отдельного растения (`plant_instance_bbox`) — прямоугольник вокруг одного экземпляра растения;
- маска отдельного растения (`plant_instance_mask`) — пиксельная область, принадлежащая одному растению;
- точка основания стебля (`stem_base_point`) — координата места выхода стебля из субстрата;
- точка воздействия (`action_point`) — координата наведения рабочего органа;
- многоугольник запрещённой зоны (`forbidden_zone_polygon`) — область, где действие запрещено.

### 4.2. Биологический уровень

Этот уровень отвечает на вопрос: «что это за растение или объект?»

- целевой вид/порода;
- сорный вид, если известен;
- неизвестное растение;
- мох/водоросли/зелёный налёт;
- повреждённый сеянец;
- сухой остаток растения;
- мусор/субстрат/тень/блик.

### 4.3. Управленческий уровень

Этот уровень отвечает на вопрос: «что делать?»

- сохранить;
- удалить;
- оставить на проверку оператору;
- не действовать из-за риска;
- повторно сфотографировать;
- требуется ручная агрономическая оценка.

Нельзя считать, что `weed = remove`, а `seedling = keep` во всех случаях. Лишний целевой всход в ячейке может быть `crop_seedling`, но управленческое решение для него — `remove`. Повреждённый целевой сеянец может быть биологически `crop_seedling`, но технологически подлежать выбраковке. Это надо фиксировать явно.

## 5. Минимальный состав одной записи набора данных

Для каждого изображения рекомендуется хранить не только картинку и `.txt`-разметку YOLO, но и расширенный дополнительный файл с тем же базовым именем.

### 5.1. Рекомендуемый состав файлов

```text
dataset_root/
  raw/
    images/
      2026-06-07_session01_tray0001_view01.jpg
    metadata/
      2026-06-07_session01_tray0001_view01.json
  annotations/
    yolo_detection/
      2026-06-07_session01_tray0001_view01.txt
    cells/
      2026-06-07_session01_tray0001_view01.cells.json
    action_points/
      2026-06-07_session01_tray0001_view01.actions.json

    session01_camera_calibration.json

    image_манифест.csv
    split_manifest.csv
    annotation_audit.csv
    dataset_version.json
  processed/
    prepared_seedlings_v001/
```

### 5.3. Что обязательно фиксировать

Минимально обязательные поля:

- уникальный `image_id`;
- `session_id`;
- `tray_id`;
- дата и время;
- место съёмки;
- тип кассеты и размер сетки;
- культура/вид целевого растения;
- возраст растений;
- камера и параметры съёмки;
- освещение;
- оператор;
- группа для разбиение;
- статус разметки;
- версия онтологии классов.

Если этих полей нет, потом будет сложно доказать, что тестовая выборка действительно независим, а модель не выучила частные особенности одной съёмочной сессии.

## 6. Протокол съёмки: что надо стандартизировать

### 6.1. Камера и оптика

Нужно заранее выбрать, будет ли набор данных имитировать будущую промышленную установку или собираться «как получится». Для продукта предпочтителен первый вариант.

Рекомендации:

- использовать одну или несколько фиксированных камер, но обязательно сохранять `camera_id`;
- зафиксировать высоту камеры относительно плоскости кассеты;
- зафиксировать фокусное расстояние/зум;
- отключить случайный автофокус, если он меняет масштаб и резкость между кадрами;
- по возможности использовать ручную экспозицию и фиксированный баланс белого;
- сохранять исходные изображения без пересылки через мессенджеры;
- не менять ориентацию изображения без фиксации этого факта;
- сохранять EXIF, если он корректный;
- если EXIF ненадёжен, дублировать параметры в JSON/CSV.

Нельзя делать набор данных из изображений, которые прошли через неизвестную компрессию, автоматическое улучшение, кадрирование или поворот. Это нарушит воспроизводимость.

### 6.2. Разрешение и масштаб

Для будущего удаления важен не только `mAP`, но и физическая точность. Поэтому для каждого режима съёмки надо знать масштаб:

```text
px_per_mm_x
px_per_mm_y
field_of_view_mm
working_distance_mm
```

Если масштаб неизвестен, нельзя корректно оценивать ошибку наведения. Ошибка `25 px` может быть допустимой или катастрофической в зависимости от масштаба.

### 6.3. Калибровка

Минимальный набор калибровочных данных:

- снимок шахматной доски или другой калибровочной мишени для оценки внутренней калибровки камеры;
- снимок кассеты с известными геометрическими маркерами;
- координаты углов рабочей области в пикселях;
- размеры кассеты и ячеек в миллиметрах;
- проверка искажений объектива;
- матрица преобразования `image_px → tray_mm`;
- дата и условия калибровки;
- критерий валидности калибровки.

Если планируется исполнительный механизм, нужен отдельный контур:

```text
image_px → tray_mm → robot_frame_mm → actuator_command
```

Набор данных должен позволять оценить ошибку на каждом переходе, а не только качество детекции.

### 6.4. Освещение

Нужно покрыть реальные режимы освещения, но не хаотично. В метаданных должны быть отражены:

- искусственное освещение;
- естественный свет;
- смешанный свет;
- блики от влажного субстрата;
- тени от конструкции;
- пересветы;
- недоэкспонированные зоны;
- разное время суток;
- состояние после полива и до полива.

Если все сорняки сняты при одном освещении, а целевые сеянцы при другом, модель может выучить освещение вместо биологии.

### 6.5. Положение кассеты

Нужно включить:

- идеально выровненные кассеты;
- небольшие повороты;
- смещения относительно кадра;
- частично обрезанные кассеты;
- кассеты с повреждёнными краями;
- кассеты с грязью на краях;
- кассеты разных партий/цветов/материалов;
- кассеты с деформированными ячейками.

Но важно разделить два режима:

1. **контролируемый лабораторный набор данных** — кассеты расположены строго, фон стабилен;
2. **продуктовый набор данных** — допускаются реальные вариации производственной линии.

Их нельзя смешивать без указания домена.

### 6.6. Фон и окружающая сцена

Если в кадре есть только идеальная кассета на чистом столе, модель может провалиться на производстве. Надо включать:

- реальные столы/тележки/стеллажи;
- руки оператора как отрицательные/запрещённые случаи, если они возможны в реальной эксплуатации;
- инструменты рядом с кассетой;
- капли воды;
- грязь;
- этикетки;
- маркировку кассет;
- частично видимые соседние кассеты.

При этом для критичных для безопасности объектов лучше не обучать модель «удалять», а обучать систему останавливать действие или переводить случай оператору.

## 7. Биологическое покрытие набора данных

### 7.1. Стадии роста

Набор данных должен покрывать несколько стадий:

- до появления всходов;
- начало прорастания;
- семядольная стадия;
- ранние настоящие листья;
- стадия, когда листья перекрываются;
- переросшие растения;
- повреждённые или угнетённые растения;
- высохшие/погибшие растения;
- повторный рост после неполного удаления, если изучается воздействие.

Ранние стадии особенно важны: именно там визуальное различие между сорняком и целевым растением может быть минимальным.

### 7.2. Видовой состав

Нужно фиксировать:

- целевой вид;
- сорт/породу/партию семян;
- вероятные виды сорняков;
- случаи неизвестных сорняков;
- наличие мха, водорослей, плесени или зелёного налёта;
- повреждённые целевые растения, которые визуально похожи на сорняки.

Если сорняки размечаются как единый класс `weed`, всё равно полезно хранить экспертный `weed_species` там, где он известен. Позже это позволит проверить, на каких видах модель проваливается.

### 7.3. Плотность и перекрытия

Надо специально собирать сложные случаи:

- один сеянец в ячейке;
- два сеянца;
- три и более сеянцев;
- сеянец + сорняк;
- несколько сорняков;
- растения на границе двух ячеек;
- листья, заходящие в соседние ячейки;
- перекрытие листьев;
- очень маленькие растения;
- сильно вытянутые растения;
- растения у края ячейки;
- растения у стенки кассеты;
- растения, частично закрытые субстратом.

Для удаления особенно важны не красивые одиночные растения, а тесные и неоднозначные случаи.

### 7.4. Отрицательные примеры

Отрицательные примеры нужны обязательно:

- пустые ячейки;
- пустые кассеты;
- кассеты без сорняков;
- изображения без кассеты;
- мох/зелёный налёт без растений;
- мусор, похожий на растение;
- капли воды;
- тени;
- блики;
- повреждения субстрата;
- остатки удалённых растений;
- нерастительные зелёные объекты.

Без отрицательных примеров модель будет находить «растения» там, где их нет.

## 8. Факторный план сбора данных

Не надо собирать данные только по принципу «сфотографируем, что есть». Нужен план покрытия факторов.

| Фактор | Минимальные уровни | Зачем нужен |
|---|---:|---|
| Сессия съёмки | ≥ 3 | Проверка устойчивости к дню, освещению, оператору. |
| Возраст растений | ≥ 4 стадии | Проверка роста и изменения морфологии. |
| Освещение | ≥ 3 режима | Борьба с доменным сдвигом. |
| Состояние субстрата | сухой / влажный / после полива | Влажность сильно меняет цвет и блики. |
| Тип ячейки | центральные / крайние / угловые | Геометрия и тени отличаются. |
| Плотность растений | 0 / 1 / 2 / >2 | Нужна для `cell_state` и прореживания. |
| Наличие сорняков | нет / одиночные / множественные | Нужна для будущего класса `weed`. |
| Положение кассеты | ровно / смещено / повернуто | Нужна для устойчивости геометрии. |
| Камера | основная / альтернативная | Нужна для проверки аппаратной переносимости. |
| Питомник или зона | ≥ 2, если возможно | Нужна для внешней валидности. |

Числа выше — не формальные нормативы, а практический минимум для пилотного этапа. Для серьёзного продукта уровней должно быть больше.

## 9. Размер набора данных: считать надо не только изображения

Нельзя задавать объём только числом картинок. В кассетной задаче есть минимум четыре уровня статистической единицы:

1. изображение;
2. кассета;
3. ячейка;
4. отдельное растение;
5. кандидат на удаление.

Например, 100 изображений кассет 11×11 дают до 12 100 ячеек, но это не означает 12 100 независимых наблюдений: ячейки внутри одной кассеты зависят от одной сессии, одной партии семян, одного освещения и одного оператора.

### 9.1. Практическая поэтапная стратегия

#### Пилот `v0.0`

Цель: проверить онтологию и разметку, а не обучить финальную модель.

Рекомендуемый объём:

- 50–150 изображений;
- несколько сессий съёмки;
- минимум 2–3 стадии роста;
- минимум 10–20 сложных случаев каждого типа;
- двойная разметка части изображений;
- запуск автоматическая проверка-скриптов;
- обучение грубого базовый метод сравнения и YOLO только для диагностики ошибок.

#### Первая рабочая версия `v0.1`

Цель: получить воспроизводимый научный эксперимент для статьи.

Рекомендуемый объём:

- сотни или первые тысячи изображений, если это реально;
- не менее нескольких десятков кассет в независимом тестовая выборка;
- достаточное число ячеек классов `empty`, `single`, `multiple`;
- отдельный набор сложных случаев;
- фиксированный разбиение;
- паспорт набора данных;
- внешний или отложенный тестовая выборка, если возможно.

#### Продуктовая версия `v1.0`

Цель: проверить устойчивость к реальным условиям.

Нужны:

- данные из разных дней, партий, операторов и условий;
- редкие и аварийные случаи;
- данные с будущей промышленной камеры;
- измерения координатной ошибки;
- постконтроль результата удаления;
- логирование отказов и вмешательств оператора.

### 9.2. Баланс классов

Не надо искусственно делать одинаковое число изображений по классам, если это разрушает реальное распределение. Лучше иметь два представления:

- **реалистичное распределение** для оценки продукта;
- **обогащённый набор редких случаев** для обучения и анализа отказов.

В тестовая выборка должно быть понятно, что именно он отражает:

- реальную эксплуатационную частоту;
- стресс-тест;
- редкие сложные случаи;
- внешний домен.

## 10. Разметка: какой формат выбрать

### 10.1. Разметка в формате YOLO

YOLO-формат удобен для детекция объектов:

```text
class_id x_center y_center width height
```

Координаты нормируются на размер изображения. Этот формат хорошо подходит для текущего контура, где ожидается структура `images/` и `labels/`.

Но YOLO одной ограничивающей рамки недостаточно для всего проекта. Он не хранит:

- состояние ячейки;
- координату действия;
- неопределённость;
- связь растения с ячейкой;
- запретную зону;
- экспертный комментарий;
- биологический статус;
- маску перекрывающихся листьев;
- калибровочную информацию.

### 10.2. Когда достаточно ограничивающая рамка

Ограничивающую рамку можно использовать, если задача:

- найти кассету;
- найти растение как объект;
- построить грубую матрицу заполненности;
- получить базовый метод сравнения для статьи.

### 10.3. Когда нужна сегментация

Сегментация нужна, если:

- листья растений перекрываются;
- ограничивающие рамки разных растений сильно пересекаются;
- центр ограничивающей рамки не соответствует основанию растения;
- нужно оценить площадь растения;
- нужно отделять растение от мха/субстрата;
- нужно выбирать точку воздействия более точно.

Для будущего продукта желательно хотя бы на подмножестве данных иметь маски отдельных объектов, даже если первая модель обучается на ограничивающая рамка. Это позволит позже сравнить, насколько решение на основе ограничивающих рамок искажает координаты удаления.

### 10.4. Когда нужны ключевые точки

Для удаления могут быть полезнее ключевые точки, то есть явно размеченные координаты на объекте:

- основание стебля (`stem_base`) — место выхода стебля из субстрата;
- точка роста (`growth_point`) — участок растения, отвечающий за дальнейший рост, если его можно надёжно определить по изображению;
- точка воздействия (`action_point`) — координата наведения рабочего органа;
- центр сохраняемого сеянца (`keep_seedling_center`) — ориентировочная точка растения, которое нельзя повредить;
- ближайшая безопасная граница (`nearest_safe_boundary`) — граница зоны, ближе которой действие считается опасным.

Ключевая мысль: **если рабочий орган должен попасть в точку, эту точку надо размечать как точку, а не выводить из ограничивающая рамка эвристически**.

### 10.5. На уровне ячеек разметка

Для каждой кассеты желательно хранить таблицу ячеек:

```json
{
  "image_id": "2026-06-07_session01_tray0001_view01",
  "grid_rows": 11,
  "grid_cols": 11,
  "cells": [
    {
      "row": 0,
      "col": 0,
      "state": "empty",
      "plant_instance_ids": [],
      "weed_instance_ids": [],
      "review": false
    },
    {
      "row": 0,
      "col": 1,
      "state": "multiple_crop",
      "plant_instance_ids": ["p001", "p002"],
      "weed_instance_ids": [],
      "review": false
    }
  ]
}
```

Такой формат лучше для статьи, чем только mAP на уровне отдельных объектов, потому что конечная прикладная задача является на уровне ячеек задачей.

## 11. Правила разметки растений

Нужно написать отдельный `ANNOTATION_GUIDE.md`. Без него качество разметки будет непроверяемым.

### 11.1. Общие правила ограничивающая рамка

- Обводить видимую часть растения, а не предполагаемую невидимую часть.
- Не включать в ограничивающая рамка соседнее растение, если его можно отделить.
- Если листья двух растений перекрываются, размечать оба растения, насколько возможно.
- Если растение почти полностью закрыто и его нельзя уверенно идентифицировать, ставить `unknown` или `uncertain`.
- Если растение находится на границе двух ячеек, связывать его с ячейкой по основанию стебля, а не по листьям.
- Не размечать тени, блики, капли воды и мох как растения.
- Не использовать ограничивающая рамка всей группы растений вместо отдельных отдельные экземпляры, если задача требует удаления отдельных растений.

### 11.2. Сорняки

Правила для `weed` должны быть особенно строгими:

- `weed` ставится только при достаточной уверенности эксперта;
- если разметчик не агроном, спорные случаи идут в `unknown_plant`;
- если сорняк и целевой сеянец неразличимы на ранней стадии, это фиксируется как ограничение набора данных;
- желательно хранить `weed_species`, если эксперт способен определить вид;
- если растение технологически нежелательно, но биологически является целевым сеянцем, это `extra_crop_seedling`, а не `weed`.

### 11.3. Лишние целевые всходы

В ячейке с несколькими целевыми всходами нужно не просто указать `multiple`. Надо определить:

- какой сеянец оставлять;
- какой удалить;
- по какому критерию принято решение;
- уверен ли эксперт;
- где точка действия;
- какое безопасное расстояние до сохраняемого сеянца.

Критерий «оставить самый большой ограничивающая рамка» — допустимая базовый метод сравнения-эвристика, но не доказанный биологический критерий. Если статья утверждает оптимальность выбора, нужен агрономический протокол.

### 11.4. Повреждённые и аномальные растения

Нужно выделить случаи:

- погибший сеянец;
- повреждённый сеянец;
- деформированный сеянец;
- хлороз/изменение цвета;
- засохший остаток;
- неполное прорастание;
- растение, которое нельзя уверенно классифицировать.

Не все такие случаи надо включать в основную модель сразу. Но их надо фиксировать, иначе они попадут в данные как шум.

## 12. Разметка ячеек и сетки

### 12.1. Геометрия кассеты

Если кассета регулярная, можно строить сетку по ограничивающая рамка контейнера. Но это допустимо только при выполнении условий:

- кассета почти прямоугольна в изображении;
- камера близка к съёмка сверху;
- перспективные искажения малы или исправлены;
- границы ограничивающая рамка размечаются одинаково;
- фактическая сетка совпадает с равномерным делением.

Если эти условия не выполняются, нужен более строгий подход:

- разметка четырёх углов рабочей области;
- homography-преобразование;
- опорные точки сетки;
- явная разметка cell polygons;
- отдельная оценка ошибки сетки.

### 12.2. Состояния ячейки

Минимальная схема:

```text
0 = empty
1 = single_crop
2 = multiple_crop
3 = weed_present
4 = crop_and_weed
5 = uncertain
```

Для текущего вычислительный контур можно сводить к `0 / 1 / >1`, но исходная разметка должна быть богаче, чтобы не потерять информацию.

### 12.3. Привязка растения к ячейке

Правило должно быть одно:

- предпочтительно привязывать растение к ячейке по `stem_base`, если он размечен;
- если `stem_base` не размечен, использовать центр ограничивающей рамки как временную эвристику;
- если растение на границе и центр ограничивающей рамки вводит в заблуждение, ставить `uncertain` или вручную задавать cell id;
- если листья заходят в соседнюю ячейку, это не означает принадлежность к соседней ячейке.

### 12.4. Контроль ошибок сетки

Нужно сохранять примеры, где:

- сетка сдвинута;
- ограничивающая рамка контейнера слишком широкий/узкий;
- кассета повернута;
- крайние ячейки размечаются хуже;
- часть кассеты обрезана;
- ячейки деформированы.

Для статьи полезно отдельно показывать, как ошибка контейнера влияет на на уровне ячеек метрики.

## 13. Разметка координат удаления

### 13.1. Почему это отдельный слой

Для исполнительного механизма объектная детекция — только промежуточный шаг. Нужна точка действия и зона безопасности.

Для каждого кандидата на удаление желательно хранить:

```json
{
  "target_id": "t001",
  "image_id": "...",
  "row": 3,
  "col": 7,
  "target_instance_id": "p045",
  "target_type": "extra_crop_seedling",
  "action_point_px": [1280.5, 764.2],
  "action_point_mm": [54.1, 31.8],
  "point_type": "stem_base",
  "uncertainty_radius_px": 12,
  "forbidden_zone_instance_ids": ["p044"],
  "min_distance_to_keep_px": 38,
  "human_review_required": false,
  "decision_rule": "expert_selected_best_seedling",
  "annotator_id": "agronomist_01"
}
```

### 13.2. Обязательные поля

- тип цели: сорняк, лишний целевой всход, неизвестное растение;
- точка действия;
- основание для решения;
- сохраняемое соседнее растение;
- расстояние до сохраняемого растения;
- флаг сомнительности;
- рекомендуемое действие: удалить / не удалять / оператор;
- координаты в пикселях;
- координаты в миллиметрах, если калибровка доступна.

### 13.3. Запрещённые зоны

Для безопасной системы нужны не только цели, но и запреты:

- зона вокруг сохраняемого сеянца;
- зона за пределами кассеты;
- зона около стенки ячейки, если рабочий орган может повредить кассету;
- зона блика или плохой видимости;
- зона, где уверенность модели ниже порога;
- зона с рукой/инструментом/посторонним объектом.

Если набор данных не содержит запрещённых зон, правила безопасного принятия решений придётся строить на догадках.

## 15. Разбиение: главная защита от самообмана

### 15.1. Нельзя делить случайно по изображениям

Если одна кассета снята 10 раз, эти 10 кадров нельзя случайно распределять между обучающая выборка и тестовая выборка. Модель увидит почти тот же объект в обучении и тесте.

Делить надо по группам:

- `tray_id`;
- `session_id`;
- дата съёмки;
- партия семян;
- теплица/стол;
- оператор;
- камера;
- серия кадров.

В текущем проекте уже предусмотрен `group_regex`; его надо использовать обязательно, если имя файла содержит информацию о серии/кассете/дате.

### 15.2. Рекомендуемая схема разбиение

Минимально:

```text
обучающая выборка (`train`):       70%
валидационная выборка (`val`): 15–20%
тестовая выборка (`test`):      10–15%
```

Но проценты не главное. Главное — независимость групп.

Более строгая схема:

```text
обучающая выборка (`train`) — основные условия;
валидационная выборка (`val`) — условия, похожие на обучающую выборку, для настройки порогов;
внутренняя тестовая выборка (`test_internal`) — новые кассеты из тех же условий;
временная тестовая выборка (`test_temporal`) — другая дата или стадия роста;
внешняя тестовая выборка (`test_external`) — другой питомник, камера или партия, если возможно;
стрессовая проверочная выборка (`стрессовая проверка_test`) — блики, грязь, перекрытия, редкие случаи.
```

### 15.3. Не трогать тестовая выборка

Тестовую выборку нельзя использовать для:

- выбора архитектуры;
- подбора `conf`/`iou`;
- выбора искусственных преобразований;
- ручной доразметки после просмотра ошибок модели;
- доразметка по информативным примерам;
- выбора финального сохранённое состояние модели.

Если тестовая выборка использовалась для решений, он больше не является честным тестовая выборка.

### 15.4. Искусственные преобразования только после разбиения

Правило жёсткое:

> сначала разбиение по группам, потом искусственные преобразования только в обучающей выборке.

Нельзя искусственно расширять весь набор данных, а потом делить. Иначе в тестовой выборке попадут почти повторяющиеся изображения обучающих изображений.

### 15.5. Проверка почти повторяющиеся изображения

Нужно проверять:

- одинаковые имена файлов;
- одинаковые хэши;
- перцептивный хеш;
- изображения с одинаковым `tray_id` в разных частях разбиения;
- искусственно преобразованные версии в валидационная/тестовая выборки;
- серии видео, попавшие в разные части разбиения.

## 16. Искусственные преобразования: что можно и что опасно

### 16.1. Допустимые искусственные преобразования

Для обучающая выборка можно использовать:

- умеренное изменение яркости;
- умеренное изменение контраста;
- небольшие цветовые вариации;
- небольшой шум;
- небольшие повороты, если они соответствуют реальной установке;
- лёгкий размытие, если он реалистичен;
- кадрирование только если он не разрушает смысл кассеты и разметку.

### 16.2. Опасные искусственные преобразования

Осторожно с:

- вертикальным зеркальное отражение, если ориентация кассеты технологически значима;
- сильным сдвиг оттенка, который делает растение небиологичного цвета;
- большими поворотами, если на производстве кассета всегда ориентирована;
- кадрированием, которое удаляет часть кассеты и ломает сетку;
- масштабированием без корректной пересборки ограничивающая рамка;
- аугментацией валидационная выборкаidation/тестовая выборка;
- искусственное расширение данныхми, имитирующими невозможные условия.

### 16.3. Искусственное расширение данных не заменяет реальные данные

Если нет изображений после полива, синтетическое затемнение не доказывает устойчивость к влажному субстрату. Если нет настоящих перекрытий растений, случайный кадрирование не создаст биологически валидные перекрытия.

## 17. Контроль качества разметки

### 17.1. Двойная разметка

Рекомендуется двойная независимая разметка части набора данных:

- минимум пилотного поднабора;
- всех сложных классов;
- всех `weed`/`unknown` случаев;
- всех action points;
- части тестовая выборка.

После этого нужен согласование спорных случаев-протокол: эксперт решает расхождения, а не просто берётся среднее.

### 17.2. Что измерять

Для ограничивающая рамка:

- согласованность классов;
- IoU между разметчиками;
- различие центров ограничивающая рамка;
- различие размеров ограничивающая рамка;
- частота пропущенных объектов.

Для на уровне ячеек:

- совпадение состояния ячейки;
- согласованность `empty/single/multiple/weed`;
- частота `uncertain`;
- ошибки на границах ячеек.

Для action points:

- расстояние между точками разных экспертов;
- доля случаев, где эксперты выбирают разные растения для удаления;
- доля случаев, отправленных на проверка оператором;
- зависимость расхождений от стадии роста и перекрытий.

### 17.3. Эталонный набор

Нужно создать небольшой эталонный набор:

- размечен лучшим экспертом;
- не меняется без версии;
- используется для обучения новых разметчиков;
- используется для проверки дрейф качества разметки;
- содержит типичные и сложные случаи.

### 17.4. Скрипты автоматической проверки

Автоматически проверять:

- есть ли метка для каждого изображения;
- нет ли метки без изображения;
- все координаты YOLO в диапазоне `0..1`;
- ширина/высота ограничивающая рамка положительны;
- class_id входит в допустимый список;
- нет ли слишком маленьких/слишком больших ограничивающая рамка;
- нет ли изображений с нулевым размером;
- не перепутаны ли классы `container` и `seedling`;
- нет ли искусственно преобразованных файлов в исходные данные;
- нет ли почти повторяющиеся изображения между частями разбиения;
- есть ли редкие классы в валидационная/тестовая выборки;
- нет ли пустого тестовая выборка для класса `weed` или `multiple`.

- доля пропущенный сорняк / пропущенный лишний целевой всход.

### 19.4. Метрики с учётом цены ошибок

Обычная доля верных решений недостаточна, потому что разные ошибки имеют разную цену.

Пример матрицы стоимости:

| Ошибка | Цена |
|---|---:|
| Пропустить сорняк | средняя |
| Пропустить лишний целевой всход | средняя |
| Отправить оператору | низкая/средняя |
| Удалить сорняк неточно, но без вреда | средняя |
| Повредить сохраняемый сеянец | высокая |
| Сработать вне кассеты | высокая |
| Сработать при постороннем объекте | критическая |

Для продукта лучше иметь консервативную систему с большим числом `human_review_required`, чем агрессивную систему с редкими, но опасными ложными удалениями.

## 21. Доразметка по информативным примерам: полезно, но опасно

Доразметка по информативным примерам — это процесс, при котором уже обученная промежуточная модель помогает выбрать следующие изображения для ручной разметки. Обычно выбираются случаи с низкой уверенностью модели, расхождением между несколькими моделями, редкими условиями съёмки или ошибками оператора. Такой подход полезен, но может испортить честность оценки, если смешать его с тестовой выборкой.

Правила:

- первичная тестовая выборка формируется до начала доразметки и не используется для выбора новых данных;
- модель предлагает кандидатов для доразметки только из пула неразмеченных изображений (`unlabeled_pool`), то есть из данных, которые ещё не входят в обучающую, валидационную или тестовую часть;
- все добавления в обучающую выборку версионируются;
- фиксируется причина добавления изображения: низкая уверенность модели, расхождение прогнозов, редкое условие, отказ оператора или установки;
- изображения из тестовой выборки нельзя добавлять в обучающую выборку;
- ошибки тестовой выборки нельзя использовать для выбора следующей партии разметки, если тестовая выборка должна оставаться честной.

## 23. Возможные утечки данных

### 23.1. Утечка через почти повторяющиеся изображения

Происходит, если похожие кадры одной кассеты попали в разные части разбиения.

Защита:

- групповое разбиение;
- `tray_id` в имени и метаданные;
- перцептивный хеш;
- запрет искусственных преобразований до разбиения.

### 23.2. Утечка через фон

Если сорняки встречаются только на одном столе или в одной теплице, модель может выучить фон.

Защита:

- распределить сорняки по разным условиям;
- фиксировать место съёмки;
- анализировать метрики по доменам;
- тестировать на новой зоне.

### 23.3. Утечка через имена файлов

Если последующий скрипт обработки случайно использует имя файла или порядок файлов, возможна скрытая утечка.

Защита:

- не передавать модели метаданные, если это не часть задачи;
- фиксировать разбиение явно;
- проверять, что скрипты не сортируют данные по классу/дате так, что разбиение становится предсказуемым.

### 23.4. Утечка через ручную доразметку

Если после просмотра ошибок на тестовая выборка исправить только разметку тестовой выборки или изменить правила под тестовая выборка, оценка станет смещённой.

Защита:

- замораживать тестовая выборка;
- любые исправления делать через новую версию;
- сохранять журнал изменений;
- после существенных изменений формировать новый внешняя тестовая выборка.

### 24.2. Хэши

## 26. Практический протокол сбора данных

### 26.1. До съёмки

Проверить:

- утверждена онтология классов;
- написан `ANNOTATION_GUIDE.md`;

- камера закреплена;
- баланс белого/exposure зафиксированы или логируются;
- определён список условий, которые надо покрыть;
- определён ответственный за агрономическую валидацию;
- создана структура каталогов;
- настроен резервная копия.

### 26.2. Во время съёмки

Фиксировать:

- каждую кассету;
- каждый повторный кадр;
- случайные проблемы;
- полив/влажность;
- положение кассеты;
- отклонения от протокола;
- калибровочные кадры в начале и конце сессии;
- примеры сложных случаев;
- пустые/отрицательные случаи.

Не удалять неудачные кадры сразу. Иногда они полезны как стрессовая проверка/примеры отказов. Но их статус надо помечать.

### 26.3. После съёмки

Сразу выполнить:

- проверку целостности файлов;
- генерацию манифест изображений;
- проверку дубликатов;
- проверку полнота метаданных;
- резервное копирование исходные данные;
- первичную сортировку по условиям;
- отбор пилотной партии для разметки;
- запись отчёт о съёмочной сессии.

## 28. Как организовать имена файлов

Хорошее имя файла помогает избежать утечек и потери метаданные.

Пример:

```text
20260607_siteA_gh02_session01_tray0001_view01_rgb.jpg
```

Поля:

- дата;
- площадка;
- теплица;
- сессия;
- кассета;
- вид;
- модальность.

Но важное ограничение: **не полагаться только на имя файла**. Все поля должны дублироваться в метаданные.

### 28.1. Идентификатор группы

Для разбиение нужен `group_id`, например:

```text
siteA_gh02_20260607_tray0001
```

Все кадры с одним `group_id` должны попадать в один разбиение.

## 29. Что делать с видео

Видео может быть полезно, но оно создаёт риск почти повторяющееся изображение утечка.

Если снимается видео:

- хранить исходное видео отдельно;
- извлекать кадры с заданным интервалом;
- присваивать всем кадрам одного прохода один `sequence_id`;
- делить обучающая выборка/тестовая выборка по `sequence_id`, а не по кадрам;
- не использовать соседние кадры в разных частях разбиения;
- хранить временная метка кадра;
- не считать тысячи кадров одного видео тысячами независимых изображений.

Для модели можно использовать кадры, но для статистической оценки независимость должна считаться по кассетам/сериям.

## 30. Работа с сомнительными случаями

Нельзя заставлять разметчика выбирать класс там, где он не уверен.

Нужны статусы:

```text

unknown
```

Сомнительные случаи полезны:

- для анализа границ применимости;

- для стрессовая проверка-тестовая выборка;
- для доразметка по информативным примерам.

Но они опасны как обычные метки обучающей выборки.

## 32. Аспекты безопасности на уровне данных

## 33. Базовые линии, которые надо предусмотреть

Для статьи нужны базовый метод сравнения. Набор данных должен позволять честное сравнение.

### 33.1. Простые базовый метод сравнения

- сегментация по цвету HSV и зелёной компоненте;
- связные компоненты;
- порог по площади;
- known container ограничивающая рамка;
- равномерная сетка;
- эвристика «оставить самый крупный ограничивающая рамка».

Такие базовый метод сравнения полезны: если сложная модель выигрывает мало, научная новизна слабая.

### 33.2. Нейросетевые базовый метод сравнения

- YOLO-nano/small;
- segmentation model на подмножестве;
- классификатор cell кадрированиеs;
- двухэтапная схема: tray → cells → классификатор отдельных ячеек;
- классический CV базовый метод сравнения.

### 33.3. Честность базовый метод сравнения

Нельзя сравнивать YOLO сквозная с базовый метод сравнения, которому дан эталонная разметка контейнер, и делать вывод «YOLO лучше/хуже» без уточнения. Надо явно писать, какие сведения доступны каждому методу.

## 40. Таксономия ошибок

Нужно заранее классифицировать ошибки:

### 40.1. Ошибки изображения

- расфокусировка;
- смаз из-за движения;
- пересвет;
- тень;
- блик;
- слишком маленький масштаб;
- кассета обрезана;
- неправильная ориентация;
- загрязнение объектива.

### 40.2. Ошибки геометрии

- неверный ограничивающая рамка контейнера;
- неверные углы;
- сдвинутая сетка;
- неправильное число строк/столбцов;
- перспективное искажение;
- деформация кассеты.

### 40.3. Ошибки биологии

- сорняк похож на целевой сеянец;
- повреждённый сеянец принят за сорняк;
- мох принят за растение;
- листья перекрывают основание;
- слишком ранняя стадия;
- высохший остаток принят за живое растение.

### 40.4. Ошибки решения

- выбран не тот сеянец для удаления;
- action point попал в лист, а не основание;
- цель слишком близко к сохраняемому сеянцу;
- модель уверена в сомнительном случае;
- система не отправила случай оператору.

### 40.5. Ошибки продукта

- исполнительный механизм не попал в точку;
- калибровка устарела;
- кассета сместилась после снимка;
- воздействие не уничтожило цель;
- повреждён соседний сеянец;
- возник опасная ситуация.

- нет искусственных преобразований в валидационная/тестовая выборки;
- есть независимый тестовая выборка;
- есть базовый метод сравнения;
- есть на уровне ячеек metrics;
- есть доверительные интервалы;
- есть анализ отказов;
- известны ограничения;
- результаты воспроизводятся из кода;
- не заявляется больше, чем покрыто данными.

Если этих условий нет, набор данных годится для инженерной разведки, но не для сильного научного утверждения.

## 43. Минимальные критерии готовности к прототипу удаления

Для перехода от набора данных к физическому удалению нужны дополнительно:

- калибровка пикселей в миллиметры;
- оценка ошибки наведения;
- action point разметка;
- forbidden zones;
- безопасность метки;
- критерий `human_review_required`;
- протокол после воздействия контроля;
- оценка повреждения соседних сеянцев;
- аварийный останов;
- журнал действий;
- тесты на отказ камеры/света/калибровки.

Без этого нельзя обоснованно говорить о готовности к производственному внедрению.

## 51. Главные ошибки, которых надо избежать

1. Добавить класс `weed` без агрономической разметки.
2. Считать центр ограничивающей рамки точкой удаления.
3. Делить данные случайно по изображениям.
4. Аугментировать данные до разбиения.
5. Смешать старые и новые подготовленные наборы данных.
6. Использовать тестовая выборка для подбора порогов.
7. Не хранить метаданные.
8. Не фиксировать камеру и калибровку.
9. Не размечать отрицательные случаи.
10. Не иметь `uncertain` и заставлять разметчика угадывать.
11. Оценивать только `mAP` и игнорировать на уровне ячеек/на уровне целей удаления метрики.
12. Не проверять согласованность разметчиков.
13. Не отделять задачу прореживания от задачи сорняков.
14. Не измерять ошибку в миллиметрах.
15. Делать вывод о промышленной готовности по оценке на заранее собранном наборе данных.

## 52. Итоговая рекомендуемая стратегия

На ближайшем этапе лучше собрать не «большой, но грязный» набор данных, а **меньший, но методологически чистый**:

- строгая онтология;
- полные метаданные;
- групповое разбиение;
- пилотная двойная разметка;
- автоматическая проверка;
- на уровне ячеек эталонная разметка;
- action point хотя бы на подмножестве;
- калибровка;
- честный базовый метод сравнения;
- замороженная тестовая выборка;
- документация.

После этого можно масштабировать сбор. Если начать с хаотичного набора изображений, проект быстро упрётся в неустранимые вопросы рецензента: «что именно размечено?», «почему тестовая выборка независим?», «как связаны пиксели и физическое удаление?», «почему ошибка модели безопасна?», «какой агрономический критерий удаления?». Эти вопросы надо закрывать уже на этапе проектирования набора данных.
